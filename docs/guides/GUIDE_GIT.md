# Git 작업

브랜치 생성·전환, 작업 변경의 이동, 커밋·push·tag·PR·병합·브랜치 정리 전에 관련 절을 읽는다.

- stage·커밋·push·PR·병합 전에는 [공개 전 검사](GUIDE_PUBLISH.md)를 적용한다. 사용자가 PR 생성·push·CI 확인·머지를 명시적으로 맡긴 범위는 이미 승인된 것으로 보고 반복 확인하지 않는다. 이 경우 diff·커밋 메시지와 검증 결과를 작업 중 알리고 모든 실제 CI check 성공을 확인해 병합한다.

- 브랜치 운영은 `main` → `develop` → `feature/<작업명>`을 따른다. `main`은 배포 가능한 코드, `develop`은 개발 통합, `feature/*`는 하나의 논리적 작업을 담당한다. 프론트엔드·백엔드 상시 브랜치(`fe`, `be`)는 두지 않으며 한 기능에 필요한 양쪽 변경을 같은 feature 브랜치에서 처리한다.
- 브랜치를 임의로 만들거나 바꾸지 않는다. 사용자 확인을 받은 최초 `develop`은 최신 `main`에서 만들고, 이후 새 `feature/*`는 최신 `develop`에서 분기한다. 기존의 '모든 작업 브랜치를 main에서 분기' 규칙은 이 규칙으로 대체한다.
- 작업 시작 전 현재 브랜치, 미커밋 변경, 원격 상태를 확인한다. `main`·`develop`에서 직접 기능을 구현하지 않는다. 진행 중인 변경은 백업·보존하고 작업 브랜치로 옮기며, 기존 사용자 변경을 덮어쓰지 않는다.
- 브랜치명은 `feature/story-input`, `feature/saju-search`, `feature/share-card`처럼 짧은 영문 소문자와 hyphen으로 작업 목적을 나타낸다. 기능·수정·문서 작업을 논리적 단위로 묶으며, 현재 범위에서는 별도 `release/*`·`hotfix/*` 체계를 선행 도입하지 않는다.
- 기본 병합 흐름은 `feature/*` → PR → `develop` → 배포 PR → `main`이다. feature PR의 대상은 `develop`으로 지정하고 관련 검사·diff 검토 후 병합한다. 배포 전 `develop`의 통합 상태와 릴리스 검증을 확인한다. `main`에 별도 수정이 반영되면 다음 작업 전에 `develop`에도 동기화한다.
- 병합 대상 브랜치가 변경되면 작업 브랜치에 반영하고 충돌을 해결한 뒤 영향받은 검증을 실행한다. 공유 브랜치의 이력을 임의로 재작성하거나 force push하지 않는다. 작업 브랜치는 병합·보존 상태와 사용자 승인을 확인한 뒤 정리한다.
- 커밋 전 diff와 메시지 초안을 보여주고 명시적 승인을 받는다. push와 tag는 각각 별도 승인을 받는다. 이미 주어진 명시적 승인은 다시 묻지 않는다.
- 커밋 메시지는 한 줄 `[PREFIX] type: 제목`을 쓰며 아래 영역·유형 기준을 따른다. 프로젝트명 약자 등 목록 밖 접두사를 임의로 만들지 않고 AI 생성 문구나 공동 작성자 표기를 넣지 않는다.
- 한 커밋은 독립적으로 검증 가능한 하나의 논리적 변경으로 묶는다. 관련 구현·테스트·문서를 파일 종류만으로 나누지 않는다.
- PR 생성·게시와 공개 배포는 사용자 요청에 포함될 때 수행한다. 이미 요청받은 범위의 준비·수정·검증은 재승인 없이 진행한다. 다른 작업의 PR 초안은 덮어쓰지 않는다.
- `main`·`develop` 직접 push는 하지 않고 PR로 통합한다. 이 문서의 규칙은 에이전트 작업 절차이며 GitHub branch protection을 자동 설정하거나 강제하지 않는다.

## 커밋 영역과 변경 유형

| PREFIX | 적용 범위 |
| --- | --- |
| `BE` | 서버·API·DB 스키마/쿼리·사주 계산 로직·서버 모델 연동 |
| `FE` | 페이지·브라우저 UI·사용자 상호작용·공유 카드 렌더링 |
| `COMMON` | 공용 모듈·계약 또는 여러 영역에 걸쳐 함께 검증해야 하는 하나의 작업 |
| `INFRA` | Node 런타임·앱 빌드 환경·CI·컨테이너·배포 설정 |
| `TOOLING` | Codex 설정·스킬·훅·Jev 하네스·개발/보안/공개 검사 도구 |
| `DATA` | 이름 목록·도시 좌표·규칙표 등 데이터와 출처·검수 메타데이터 |

유형은 `feat`(기능), `fix`(오류 수정), `refactor`(동작 유지 구조 개선), `perf`(성능), `test`(테스트), `docs`(문서), `build`(빌드/의존성), `ci`(CI), `chore`(유지보수), `style`(동작에 영향 없는 서식), `revert`(되돌리기)를 사용한다. 변경 영역이 분명하면 해당 PREFIX를 선택하고, 단지 여러 파일을 바꿨다는 이유로 COMMON을 쓰지 않는다.

문서·테스트는 대상 영역을 따른다. 예: `[BE] test: 절입 경계 회귀 검사 추가`, `[INFRA] build: Node 보안 패치 버전 고정`, `[TOOLING] feat: 공개 전 검사 추가`, `[DATA] fix: 도시 경도 출처 정정`, `[COMMON] docs: 저장소 작업 규칙 정리`. 기능과 관련 테스트·문서는 같은 논리적 커밋에 포함하며 파일 종류만으로 나누지 않는다. 이 구분은 FE·BE 상시 브랜치를 만들라는 뜻이 아니다.

근거: [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)는 type과 선택적 scope를 구분하고, [Angular 기여 가이드](https://github.com/angular/angular/blob/main/contributing-docs/commit-message-guidelines.md)도 저장소별 scope를 정한다. `[PREFIX] type: 제목`은 사용자가 선택한 이 저장소의 형식이며 표준의 `type(scope): 제목`과는 다르다.
