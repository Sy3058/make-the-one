## 도입 전 해결할 문제

1. **CSV의 코드 변환 오류.** `gov/cleaner.py:25`부터 모든 `cd`에 `chr(int(cd, 16))`를 적용한다. `a0111`은 실제 법원 조회에서도 `codetype=A`인 전용 코드인데 CSV는 미할당 U+A0111로 만든다. F 코드 28개도 Unicode 사적 사용 영역이다. A/F 합계 405개는 표준 문자로 자동 승격하지 않고 원래 코드·독음·검토 상태로 격리해야 한다. `type=0/2` 9,055개는 표준 문자 처리 후보이며 곧바로 검증 완료/추천 가능하다는 뜻은 아니다. 코드포인트는 UTF-16 한 단위로 자르거나 NFC/NFKC로 임의 통합하지 않는다.
2. **빈 독음/뜻과 미기재 뜻.** `25874`는 `ineum`·`in`이 모두 비고 `dic`만 `계`다. `a028d`는 독음 `원`, 빈 `in`, `dic=원: 동산(원)`이다. 그 외에도 `in`이 독음만 반복하는 항목이 많다. `dic`은 일반 사전 독음일 수 있어 허용 독음의 대체 근거로 사용하지 않는다. `753`은 빈 값도 포함하는 단순 문자열 비교 수치이며 실제 뜻 완전성/오류율 판정은 아니다.
3. **CSV의 정보 손실.** CSV는 `in`, `dic`, `isin`, `type`을 버리고 여러 독음을 하나의 `hangul` 문자열로 보존한다. 여러 독음이면 자음 탐색도 일치하지 않아 빈 자음이 된다. JSON에서 독음과 연결된 훈을 파싱하고 원문을 함께 보존해야 한다. 예를 들어 `瑞`의 `in`에는 `서`가 있지만 `dic`은 `단`이어서 `dic`의 독음을 그대로 허용하면 틀린 이름이 될 수 있다.
4. **획수 자료로 사용할 수 없음.** 전체 행에서 획수와 부수 조회값이 0이다. 미확인 값이며 실제 0획/오행으로 해석하지 않는다. 뜻 기반 오행 분류도 제공하지 않는다.
5. **수집기의 완전성·복구 보장 부재.** `gov/crawler.py:36`의 빈 결과 `break`는 같은 자음의 나머지 독음 조회도 중단한다. 요청 timeout, 오류 응답 재시도/실패 종료, 페이지 총수 대조, 수집 일시/원문 해시, 원자적 최종 출력도 없다. 수동 독음표 487개에는 원본에 등장하는 `녈`, `늘`이 없다. 이것만으로 실제 누락을 확정하지는 않지만 전체 수집 근거로는 불충분하다. 같은 코드를 재실행하는 대신 완전성 검증이 있는 별도 수집/검증 절차가 필요하다.

## 현재 공식 응답과의 대조

2026-11-04 공식 `listUnicodeByKsnd`에서 `ksnd=ac00`(가), `ext=0`, `pgmode=1`, `pgno=1`, `pgsize=10000`으로 한 번 조회했다. `errno=0`, `resultcount=51`, `pglast=1`이며 51개 코드의 `isin`, `ineum`, `in`, `dic`이 저장소와 모두 일치했다. 기존 JSON에서 가 독음을 가진 코드의 추가/누락도 없었다. 응답 SHA-256: `83f7b15d66429fb740cdad4099c2893588c6a47ece0e28947b5920792cd4cec5`.

공식 `unicodeInfo&code=a0111`도 한 번 조회해 전용 코드 A와 인명용 여부/독음 가를 확인했다. 현재 프로젝트 `data/names.json`의 검증된 33자는 모두 이 저장소에 존재하고 허용 독음 집합이 정확히 일치했다. 이 두 대조는 전체 최신성·완전성·뜻 정확성의 증명이 아니다. 전체 공식 표와 문자/독음/이체자 대조는 미실행이다.
